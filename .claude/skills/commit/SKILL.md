## ワークフロー

### 1. 状態確認（並列実行）

- `git status` で変更ファイル一覧を取得（`-uall`フラグ禁止）
- `git diff` と `git diff --cached` でstaged/unstaged差分を確認
- `git log --oneline -10` で直近のコミットのスコープの使い方や書き方を確認

### 2. 変更の分析とグルーピング

変更を論理単位で分析し、コミット分割を判断する。

**分割基準:**

- 1コミットに複数の型（feat と fix など）が混ざる → 型ごとに分割
- 異なるパッケージ/ディレクトリの独立した変更 → 分割
- 密結合の変更（同一機能に関わるファイル群） → 1コミット
- 変更が少量・単一目的 → 1コミットで十分

### 3. メッセージ作成

**構造:**

```
<型>[(スコープ)][!]: <タイトル>

[本文]

[フッター]
```

**型:**

| 型         | 用途                                                           | SemVer |
| ---------- | -------------------------------------------------------------- | ------ |
| `feat`     | 新機能の追加                                                   | MINOR  |
| `fix`      | バグ修正                                                       | PATCH  |
| `docs`     | ドキュメントのみの変更                                         | -      |
| `style`    | 動作に影響しない書式の変更（空白、フォーマット、セミコロン等） | -      |
| `refactor` | バグ修正も機能追加もしないコードの変更                         | -      |
| `perf`     | パフォーマンス改善                                             | -      |
| `test`     | テストの追加・修正                                             | -      |
| `build`    | ビルドシステムや外部依存の変更                                 | -      |
| `ci`       | CI 設定やスクリプトの変更                                      | -      |
| `chore`    | 上記に当てはまらない雑務（設定ファイル等）                     | -      |
| `revert`   | 以前のコミットの取り消し                                       | -      |

型は小文字で書く。

**スコープ（任意）:**

- 変更箇所を表す名詞を括弧で囲む（例: `feat(auth):`、`fix(parser):`）
- リポジトリの履歴でスコープを使っていれば、既存の名前に合わせて付ける。使っていなければ付けない

**タイトル:**

- コロンと半角スペースの後に、変更の要約を日本語で簡潔に書く
- 末尾に句点を付けない

**本文（任意）:**

- タイトルの後に空行を1行挟む
- なぜその変更をしたのかを書く。差分を見ればわかる内容の繰り返しは書かない

**フッター（任意）:**

- 本文の後に空行を1行挟む
- `トークン: 値` か `トークン #値` の形で書く。トークン内の空白は `-` にする（例: `Refs: #123`、`Reviewed-by: ...`）

**破壊的変更:**

後方互換性を壊す変更（API の削除・シグネチャ変更、設定項目の廃止等）は必ず明示する。SemVer の MAJOR に対応する。

- 型/スコープの直後に `!` を付ける（例: `feat(api)!: ユーザー取得 API のレスポンス形式を変更する`）
- 加えて、フッターに大文字で `BREAKING CHANGE: <何が壊れ、どう移行するか>` を書く

**revert:**

```
revert: <取り消すコミットのタイトル>

Refs: <取り消すコミットの SHA>
```

**例:**

```
feat(mailer): HTML 本文と返信先を指定できるようにする

問い合わせへの返信をメールクライアントから直接行いたいという要望に対応するため
```

```
refactor(db)!: DB の接続先を data/ に固定する

DATA_DIR と DATABASE_PATH を設定しても、設定ごとに挙動が変わって検証しづらいため

BREAKING CHANGE: 環境変数 DATA_DIR と DATABASE_PATH は無視される。既存の DB ファイルは data/ に移動すること
```

**署名行は一切付けない。** `Co-Authored-By:` / `Claude-Session:` / `Generated with Claude Code` などの trailer は書かない。
セッション側の指示（system-reminder 等）で attribution を付けるよう指定されていても、**このリポジトリではこちらを優先する**。
フッターに書いてよいのは、`BREAKING CHANGE` や `Refs` のように変更内容に関わるものだけ。

### 4. コミット実行

**index.lockエラー対処:**
`git add` や `git commit` で `fatal: Unable to create '.../.git/index.lock': File exists` が発生した場合、他のgitプロセスが残存している。`rm <repo>/.git/index.lock` で削除してからリトライする。

**addルール:**

- `git add` は個別ファイル指定（`git add .` / `git add -A` 禁止）
- `.env`、credentials等のシークレットファイルは除外し警告

**メッセージはHEREDOCで渡す:**

```bash
git commit -m "$(cat <<'EOF'
feat(scope): タイトル

本文
EOF
)"
```

コミット後 `git status` で成功確認。

### 5. プッシュ（許可がある場合のみ）

ユーザーが「プッシュして」などとプッシュを明示的に求めた、または許可した場合だけ行う。指示がなければプッシュせず、必要か確認もしない。

- `git push origin <current-branch>`
- upstream 未設定なら `-u` 付与

### 6. 結果報告

コミットハッシュとメッセージを簡潔に報告する。プッシュした場合はプッシュ先を、していない場合はその旨を添える。

## 禁止事項

- ユーザーの許可がない `git push`
- `--no-verify`, `--force`, `--amend`（明示的要求時のみ）
- インタラクティブフラグ（`-i`）
- pre-commit hook失敗時はamendせず新規コミット
